# LLM Compare

LLM Compare — приложение для сравнения ответов языковых моделей на один и тот же вопрос.

Выберите 2–4 модели и отправьте один вопрос всем одновременно. Ответы отображаются рядом с временем получения; на мобильном экране переключаются вкладками. Ошибку одной модели можно повторить отдельно.

По умолчанию включён **демо-режим** с четырьмя тестовыми моделями, без API-ключа и внешних запросов к языковым моделям. Также доступен серверный адаптер CodeX Proxy API. Вопросы продолжают диалог с отдельным контекстом каждой модели. Ответы поступают независимо, частями, с безопасным Markdown.

## Использование

- По умолчанию выбраны две разные модели. Кнопка «+» справа открывает поиск и добавление; максимум — четыре модели. При двух моделях удаление недоступно.
- Enter отправляет вопрос; Shift+Enter добавляет строку. Максимум — 16 КиБ UTF-8. Исходные пробелы и переносы сохраняются.
- Во время сравнения состав моделей фиксирован. Новый черновик можно редактировать, отправка доступна после завершения.
- «Остановить» закрывает поток в браузере и запускает отмену активных запросов на сервере приложения. Полученный текст и завершённые ответы сохраняются. При потере соединения сохраняются также частичные ответы; незавершённые колонки получают явную пометку. Автоматического переподключения нет.
- «Повторить ответ» использует исходный вопрос и сохранённый контекст только выбранной неуспешной модели. Успешные колонки сохраняются. Повтор доступен для последнего вопроса до отправки следующего; автоматических повторов нет. Старые попытки сохраняются в данных беседы, актуальный ответ заменяется целиком.
- Следующий вопрос добавляется к беседе. Каждая модель получает только собственные успешные пары вопрос–ответ; неуспешная пара целиком пропускается с пометкой в шапке колонки. Thinking, ошибки и частичные ответы не входят в контекст.
- Добавленная модель начинает с пустой историей, без автоматической генерации ответов на старые вопросы. Удаление и повторное добавление модели создаёт новую колонку с пустым контекстом.
- «Новое сравнение» создаёт новую беседу, сохраняя набор моделей и черновик. Предыдущая остаётся в локальной истории, если сохранение включено.
- Контекст ограничен 16 завершёнными парами и 64 КиБ UTF-8 сериализованного запроса на модель. При превышении новый запрос не отправляется; нужно начать новое сравнение. Автоматического обрезания и платного суммирования истории нет.
- В демо-каталоге есть короткий, подробный и медленный ответы, а также модель с постоянной тестовой ошибкой. Её повтор снова возвращает ошибку — это ожидаемый сценарий для проверки восстановления интерфейса.
- «Обновить модели» запрашивает актуальный каталог, сохраняя ответы и выбранные колонки. Если модель исчезла, новое сравнение недоступно до явного сброса и замены недоступных моделей. Ошибка обновления сохраняет ответы и блокирует новые запросы до успешного обновления.

В режиме API названия и порядок моделей приходят с сервера провайдера. Предустановленных оценок скорости, точности, качества или цены нет. Время относится к конкретной попытке; стоимость и токены не вычисляются без достоверных данных API.

## Локальная история

По умолчанию включено «Сохранять на этом устройстве». В IndexedDB этого браузера сохраняются вопросы, ответы и Thinking, прошлые попытки, контекст повторов, выбранные модели, вкладка модели и черновик. Список «Сохранённые беседы» открывает предыдущие диалоги. Активная беседа вкладки запоминается отдельно в `sessionStorage` как UUID; если такого указателя нет, открывается последняя сохранённая беседа. История доступна только на том же устройстве и origin (адресе, протоколе и порте), без синхронизации с аккаунтом.

Изменения объединяются в контрольные снимки с интервалом 500 мс, а завершение запроса запускает сохранение последнего снимка сразу. Статус «Сохранено на устройстве» появляется после успешной записи актуального состояния. При аварийном закрытии возможна потеря ещё не сохранённого хвоста; завершение страницы не гарантирует выполнение асинхронной записи. Пустое новое сравнение не создаёт запись до ввода черновика или отправки вопроса.

После перезагрузки сохранённые незавершённые попытки показываются как прерванные, с полученным текстом и Thinking. Их вопрос–ответ не включается в контекст следующих ходов. Повтор можно запустить вручную для последнего вопроса. Автоматической генерации при восстановлении нет. Неизвестное время прерывания не заменяется нулём. Недоступный каталог или исчезнувшая модель не мешают читать сохранённые ответы; для новой генерации нужен доступный каталог соответствующего режима.

Отключение сохранения действует и после перезагрузки: новая работа остаётся в памяти, автоматическое восстановление отключено, прежние записи доступны в списке. Отключение само по себе их не удаляет. «Удалить беседу» удаляет выбранную запись, «Очистить историю» — все записи; обе операции требуют подтверждения в интерфейсе. Они недоступны во время активного запроса.

Параллельные вкладки защищены атомарной проверкой ревизии и поколения хранилища. Удалённый идентификатор получает tombstone, очистка увеличивает поколение: старый отложенный save не может вернуть удалённые данные. При конфликте автосохранение останавливается; текущий текст остаётся в памяти. Можно явно загрузить сохранённую версию или сохранить текущую беседу как новую копию. BroadcastChannel передаёт только уведомления об идентификаторах и ревизиях, без содержимого; отсутствие или задержка уведомлений не отменяет проверки в IndexedDB.

Лимиты локального снимка: 2 МиБ UTF-8 JSON, до 100 ходов и 50 прошлых попыток на колонку одного хода. В истории — до 50 сохранённых бесед; до 500 идентификаторов вместе с tombstones, после чего требуется явная очистка. Автоматического удаления старых записей нет. При переполнении, запрете IndexedDB, повреждённой записи или неподдерживаемой версии приложение сообщает о проблеме и сохраняет текущую работу в памяти. Одна повреждённая запись не удаляет остальные; неизвестная версия не читается как текущая и не перезаписывается молча. Версия схемы — 1. Ключ API, серверная конфигурация, AST, controllers и readers в снимки не входят. Сохранение и конфликты проверяются на fake-indexeddb, в jsdom и в изолированном профиле Chrome. Реальное исчерпание квоты, другие браузеры и ручная приёмка остаются отдельными проверками.

## Метрики ответов

После завершения попытки отображаются полное время, время первого содержательного фрагмента (ответа или Thinking) и время первого фрагмента ответа. Все значения измеряет сервер монотонными часами от запуска адаптера; время записи начального события клиенту не включается. Служебные события и пустые фрагменты не считаются первыми данными. Ожидание медленного клиента во время потока влияет на наблюдаемое время; это измерение конкретного запроса, а не постоянная характеристика модели. Для обычной генерации без стрима времена первых фрагментов недоступны. Для ошибки или таймаута время подписано как длительность неуспешной попытки.

После завершения запроса могут появиться отметки минимального общего времени и времени до первого фрагмента ответа. Сравниваются только успешные ответы видимых колонок на один вопрос, отдельно по каждой метрике. Для каждой отметки нужны хотя бы два известных сопоставимых значения. Пока идёт запрос или повтор, итоговые отметки последнего хода скрыты; после повтора они пересчитываются по актуальным попыткам. Сравнение использует округление исходных миллисекунд до 1 мс; равные значения дают несколько отметок. Отображение секунд с двумя знаками не определяет результат сравнения. Эти отметки не оценивают качество или точность ответа.

Входные/выходные токены и стоимость отображаются как «нет данных» (`null` в API). Адаптер пока не получает подтверждённый usage и тарифы для расчёта; оценки по длине текста не применяются. Сравнение стоимости и полный набор метрик usage/cost пока не реализованы. Метрики времени проверены локальными сценариями, live-проверка остаётся отдельной.

## Форматирование ответов

Поддерживаются заголовки, вложенные и нумерованные списки, выделение, цитаты, GFM-таблицы, код и безопасные ссылки. Блоки кода можно копировать; код не исполняется. Ссылки допускают HTTP/HTTPS и относительные адреса, открываются с защитой новой вкладки. Сырой HTML отключён, изображения заменяются текстовой пометкой без загрузки. Таблицы и код прокручиваются внутри колонки. Если форматирование не удалось, доступен исходный текст ответа.

Потоковый Markdown разбирается инкрементально: `@lezer/markdown` с GFM переиспользует фрагменты синтаксического дерева, а прикладной AST сохраняет неизменные блоки. Соседние синтаксические блоки с общим контекстом разбираются вместе, чтобы сохранить правила продолжения списков, отступов и определений ссылок. Затронутые группы преобразуются в MDAST через `mdast-util-from-markdown` с GFM, затем в безопасный React DOM через HAST. Полный накопленный ответ не проходит пакетный parse на каждое слово; отдельного полного перепарсивания на EOF нет.

Определения ссылок учитываются во всём ответе с нормализацией меток и приоритетом первого определения. Позднее определение обновляет зависимые группы; независимые AST-объекты и DOM сохраняются. Неразрешённая ссылка остаётся текстом. Для блоков используются ключи по начальной позиции и типу, без привязки к растущему концу или содержимому. Смена типа, например абзац → Setext-заголовок, может заменить соответствующий блок.

В браузере разбор выполняется в Web Worker. Фрагменты объединяются с интервалом 35 мс, одновременно обрабатывается один снимок. Подходящий результат применяется, даже если сеть уже прислала новый хвост; затем обрабатывается следующая порция. Проверяются идентификатор попытки, эпоха и версии AST. На завершении, Stop или ошибке вход запечатывается, последний полученный хвост доразбирается без искусственных закрывающих символов, worker освобождается. При сбое worker показывается точный исходный текст. Без Web Worker доступен синхронный вариант того же движка.

Большой открытый абзац, список, код или связанная группа могут требовать повторного разбора всей этой группы. Гарантия линейной стоимости для любого Markdown не заявляется; ограничение размера ответа сохраняется. Семантика проверяется относительно пакетного CommonMark/GFM-парсера на fixtures, всех границах фрагментов, случайных разбиениях и смешанном корпусе. DOM/focus/selection проверяются в jsdom и настоящем Chrome; собранный worker — также в четырёх Node.js worker threads. Эти проверки не гарантируют такую же производительность на любом устройстве.

Текстовые узлы готового AST раскрываются по словам через `Intl.Segmenter`, с сохранением пробелов, пунктуации и Unicode. Сегментируется только изменённый хвост с незавершённым словом; Markdown при кадрах анимации не перепарсивается. Один планировщик кадров обслуживает все ответы, курсор связан с диапазонами исходного текста. Незавершённое последнее слово может дождаться следующего фрагмента. При отставании порция увеличивается; узлы длиннее 8192 символов, код и таблицы обновляются блоком. На завершении или Stop принятый остаток показывается без ожидания искусственной очереди. Скрытая вкладка и `prefers-reduced-motion` отключают задержку; при отсутствии нужных API текст также показывается сразу. Анимация не меняет сохранённый raw, историю диалога и серверные метрики. Ответы не объявляются screen reader по каждому слову — используются отдельные статусы запроса.

При ширине до 1000 px используются вкладки моделей с управлением стрелками/Home/End. История на узких экранах свёрнута и раскрывается через «История бесед». Заголовки остаются закреплены в контейнере ответов. Поле вопроса учитывает изменение окна и `visualViewport`, ограничивая высоту, чтобы длинный черновик не скрывал отправку. Проверка размеров окна не заменяет проверку настоящей экранной клавиатуры устройства.

## Запуск

Требуются Node.js **24.19.0** и npm **11.17.0**. Все команды выполняются из корня репозитория.

```sh
npm ci
npm run dev
```

Интерфейс: http://127.0.0.1:5173. API: http://127.0.0.1:3001. Vite перенаправляет запросы `/api` на сервер.

Настройки необязательны. Для изменения адреса или порта сервера создайте `.env` в корне по образцу `.env.example`. Поддерживаются `LLM_MODE=mock` и `LLM_MODE=live`, без скрытой подмены режима. Серверный ключ не передаётся клиенту; mock-режим его не читает.

## Подключение API

Для локального подключения CodeX Proxy API установите в серверном `.env`:

```dotenv
HOST=127.0.0.1
PORT=3001
LLM_MODE=live
LLM_API_KEY=replace_me
```

Замените `replace_me` своим действующим ключом сервиса; пустой ключ и это значение-заглушка останавливают запуск. Реальный `.env` исключён из Git. Получение ключа и доступный лимит определяются условиями провайдера. Отправка вопроса в live-режиме обращается к внешним моделям и может расходовать лимит аккаунта.

Адаптер использует фиксированный HTTPS-адрес `https://llm.codex.so`, серверный заголовок `x-api-key`, `GET /models`, `POST /generate` и `POST /stream` с полями `prompt` и `model`. Для стрима передаётся `Accept: application/x-ndjson`. Переадресации отключены. Базовый URL и заголовки нельзя изменить из браузера. Контракт описан в [публичной OpenAPI-схеме](https://llm.codex.so/docs/json). Обработчик событий соответствует [опубликованному обработчику прокси](https://github.com/slaveeks/ai-proxy/blob/main/src/routes/stream.js); совпадение с развёрнутой версией требует реальной проверки.

Live-режим ограничен адресами loopback (`127.0.0.1`, `::1`, `localhost`); публичное размещение API в этой версии не поддерживается. Проверены контрактные сценарии на локальном HTTP-стенде, получение реального каталога и обычная генерация на `openai/gpt-5-mini`. Стриминг и отмена проверены локально, включая разрыв настоящего HTTP-соединения. Реальная генерация на остальных моделях, live-streaming, multi-turn, reasoning, usage и стоимость пока не проверялись.

Если прокси присылает reasoning-события, они отображаются отдельно в блоке Thinking серым текстом. Во время рассуждения блок открыт; при начале ответа сворачивается и остаётся доступным с клавиатуры. Повторные reasoning-фрагменты дополняют тот же блок, сохраняя ответ. При Stop или ошибке полученный Thinking сохраняется с пометкой прерывания. Длительность фазы измеряется на сервере по событиям, а не по анимации. Если таких событий нет, блок не появляется. Демо по умолчанию не выдумывает рассуждения; эта ветка проверяется управляемыми тестовыми событиями.

Прокси принимает одно поле `prompt`, поэтому сервер сериализует историю модели и текущий вопрос как JSON с версией 1 и вводной инструкцией. Первый вопрос без истории передаётся без изменений. Это текстовое представление диалога, а не API с настоящими ролями `messages`; JSON сохраняет структуру и исходные символы, но не устраняет поведенческую prompt injection.

## Проверка и сборка

```sh
npm run typecheck
npm test
npm run build
```

`npm run check` последовательно проверяет типы, тесты, сборку, собранный Markdown worker и браузерные сценарии, выводя короткий итог каждого шага. Полный журнал сохраняется в `check.log` (исключён из Git, перезаписывается при следующем запуске). При ошибке выполнение останавливается, выводятся последние 30 строк журнала шага и возвращается ненулевой код завершения. CI запускает ту же команду. Для полного вывода в терминал доступна `npm run check:verbose`. Проверки используют тестовые адаптеры и локальные HTTP-соединения, без обращений к платным моделям.

Браузерные проверки требуют Chrome/Chromium: в Windows установленный Chrome выбирается автоматически; иначе перед первым прогоном выполните `npx playwright install chromium`. Для Linux CI браузер и системные зависимости устанавливаются командой `npx playwright install --with-deps chromium`. Канал можно выбрать через `PLAYWRIGHT_CHANNEL` (например, `chrome` или `msedge`).

`npm run check:browser` запускается после сборки. Playwright создаёт временный профиль браузера, поднимает отдельный loopback fixture API на 4309 и preview на 4179, без повторного использования уже запущенных серверов и без чтения API-ключа. Проверяются размеры 320/390/768/1024/1440, sticky/overflow, клавиатура, IME-события, axe/WCAG-правила, настоящий worker, пословный показ, Stop, Thinking, одиночный retry, восстановление IndexedDB и конфликт вкладок. Для четырёх больших потоков фиксируется время ввода черновика с локальным тестовым порогом 2 с; это не универсальная гарантия задержки. Clipboard в тестах подменён, личный буфер обмена не используется. Скриншоты и трассы находятся в `test-results/browser`, исключённом из Git. Автоматические проверки не означают полного соответствия макету, ручной проверки screen reader, физической мобильной клавиатуры или live-приёмки.

`npm run check:markdown-worker` запускается после сборки и проверяет именно собранный worker без DOM: четыре параллельных потока, 16 растущих снимков с длинными незакрытыми абзацами и кодом, совпадение с пакетным эталоном и повторное использование деревьев/AST. Измерения сохраняются в `markdown-performance.log`, исключённом из Git. Этот локальный стенд также выполняет эталонные проверки на основном потоке; его задержки не являются измерением отзывчивости браузера или универсальным нормативом производительности.

После сборки `npm start` запускает API. Оставьте его запущенным и выполните `npm run preview -w @llm-compare/web` в другом терминале. Откройте адрес Vite из терминала (по умолчанию http://127.0.0.1:4173).

### Ошибка и таймаут в демо

1. Запустите интерфейс в режиме `mock`. Через «+» добавьте «Демо · Ошибка» и отправьте вопрос. Остальные колонки завершат ответы, а тестовая модель покажет ошибку.
2. Нажмите «Повторить ответ» в колонке с ошибкой. Она снова покажет тестовую ошибку, а готовые ответы останутся на экране.
3. Для воспроизведения таймаута выполните `npm test -- tests/stream-deadlines.test.ts`. Тестовый сервер с короткими таймаутами проверяет задержку первого фрагмента, паузу после частичного ответа и общий дедлайн.

## Структура

- `apps/web` — React, TypeScript, Vite, Lezer и библиотеки MDAST/HAST/GFM; собственные компоненты и CSS без UI-библиотек.
- `apps/server` — Fastify, конфигурация, каталог и адаптеры CodeX Proxy / demo.
- `packages/contracts` — общие Zod-схемы и типы публичных данных, без серверной конфигурации.
- `tests` — проверки API, параллельности и изоляции ошибок, конфигурации, выбора моделей, формы и повтора ответов.

## API

| Маршрут | Ответ |
| --- | --- |
| `GET /api/health` | `{ "status": "ok" }`, без обращения к адаптеру |
| `GET /api/models` | Версия протокола и каталога, режим, нормализованный список моделей |
| `POST /api/comparisons` | Один вопрос, 2–4 уникальных цели, отдельный результат каждой попытки |
| `POST /api/retries` | Повтор одной цели, отдельный результат попытки |

Тестовые модели помечены как демонстрационные. В live-каталоге используются имена из API и справочник провайдеров по известным префиксам ID; для неизвестного префикса отображается «Провайдер не указан». Тарифы неизвестны (`null`); доступность streaming и reasoning для конкретных реальных моделей не предполагается автоматически.

Каталог кэшируется на 60 секунд, одновременные загрузки объединяются. `GET /api/models?refresh=1` принудительно обновляет каталог. Если обновить просроченный каталог не удалось, новый запуск отклоняется до генерации. HTTP 503 каталога содержит безопасный код `CATALOG_UNAVAILABLE` или нормализованную причину от адаптера; сырой ответ провайдера не передаётся клиенту.

Запрос сравнения содержит `protocolVersion: 1`, `serializerVersion: 1`, UUID `conversationId`, `runId`, `turnId`, исходный `prompt` и массив `targets`. Каждая цель содержит UUID `columnId` и `attemptId`, `modelId` из каталога и `history` — массив завершённых `{ user, assistant }` (пустой для первого вопроса). Для повтора вместо `targets` передаётся один объект `target`. Неизвестные поля, версия сериализации, превышение количества пар или размера контекста отклоняются до генерации. Отсутствующая `serializerVersion` совместима с версией 1. Сервер stateless: клиентский снимок повтора проверяется как новый недоверенный запрос; тождество исходному контексту обеспечивается клиентом, серверной подписи снимка нет.

Без заголовка `Accept` ответ содержит те же идентификаторы запуска и массив `results`: `columnId`, `attemptId`, `modelId`, `status`, `text`, `totalMs`, `metrics` и `error`. `metrics` содержит `firstEventMs`, `firstAnswerMs`, `inputTokens`, `outputTokens`, `cost`; неизвестные значения равны `null`, не нулю. Для совместимости клиент допускает отсутствие `metrics`, сохраняя известное `totalMs`. Статусы: `succeeded`, `failed`, `timed_out`, `cancelled`; `error` равен `null` только при успехе. Время измеряется на сервере отдельно для каждой попытки.

С `Accept: application/x-ndjson` оба POST-маршрута возвращают поток событий: `run_started`, `model_started`, `answer_delta`, `reasoning_started`, `reasoning_delta`, `reasoning_ended`, `model_result`, `run_completed`. Каждая запись содержит `v: 1`, `runId`, `turnId` и последовательный `seq`; события модели содержат её идентификаторы, а `model_result` — поле `result` с результатом попытки. Фрагменты содержат `text` без изменения пробелов. Reasoning передаётся отдельно от ответа; результат при его наличии содержит `reasoning` и `reasoningMs`. При ошибке результат сохраняет частичный текст и Thinking. Клиент проверяет идентификаторы, порядок, соответствие итогового ответа/Thinking фрагментам и завершение всех попыток. Дубли `seq` пропускаются, разрывы последовательности считаются повреждением потока. EOF без `run_completed` означает обрыв; на стороне прокси успех требует `finish`, одного `text-end` недостаточно. Полная последняя JSON-запись без LF допускается, CRLF и пустые строки поддерживаются; неверный UTF-8 отклоняется.

Лимиты чтения потока: строка 4 МиБ, весь транспорт 32 МиБ, ответ и Thinking одной модели суммарно 512 КиБ. Каждый из максимум четырёх производителей ждёт записи своей порции; сервер учитывает backpressure и обрывает соединение при задержке записи более пяти секунд. На время ожидания записи таймер бездействия приостанавливается; после записи модель получает полный новый бюджет ожидания данных. Общий таймаут попытки действует также во время ожидания записи. Markdown обновляется через инкрементальный AST; ограничения открытых групп описаны в разделе форматирования.

Общий таймаут попытки — 120 секунд. Для streaming дополнительно действуют 60 секунд до первого содержательного события и 30 секунд без новых содержательных данных. Непустые content/reasoning-фрагменты считаются активностью; служебные события и пустые фрагменты не продлевают ожидание. Время получения заголовков входит в эти бюджеты: отдельный короткий таймаут headers не применяется. Для обычной генерации действует только общий таймаут. Клиент ждёт до 140 секунд, включая проверку каталога и завершение транспорта. Это настройки приложения, а не ограничения провайдера; live-проверка этих бюджетов пока не проводилась.

Совокупный лимит ответа и Thinking — 512 КиБ UTF-8, лимит HTTP-тела — 256 КиБ. При ошибке входа генерация не начинается. Повторный `runId` отклоняется с HTTP 409; защита хранится в памяти процесса пять минут после завершения. Общая ёмкость сервера — восемь одновременных попыток; при нехватке мест весь новый запуск отклоняется с HTTP 429. Прерывание локального соединения не гарантирует остановку вычислений и списания у провайдера.

При штатной остановке сервера активные запросы отменяются до ожидания закрытия соединений. Незавершённый поток закрывается без ложного успешного завершения; клиент сохраняет уже полученные части как прерванные.
